---
name: Blocking DatabaseSession inside async code
description: Recurring root cause of "bot goes offline" / Discord gateway flapping and correlated Twitch network-timeout DMs in this bot.
---

Using the sync `DatabaseSession` (blocking, `time.sleep` retries) inside an `async def` function or a loop that runs on the bot's event loop blocks the whole event loop, causing the Discord gateway heartbeat to stall (bot appears offline) and any concurrent async I/O (e.g. Twitch IRC/API calls) to time out around the same moment.

**Why:** Found and fixed in three separate files with the identical pattern — `cogs/notification_commands.py` (38 call sites), `utils/twitch_chat_monitor.py` (24 call sites, including one inside a 2-minute polling loop), and `utils/server_permissions.py`'s `ServerPermissionsManager` (a plain sync class called from many async command/loop call sites — not a standalone `async def` function, so it's easy to miss in a grep that only looks for `async def`). The third occurrence surfaced only after the first two were published and fixed — production kept flapping ("Cannot write to closing transport", gateway session invalidation) because `check_waitlist_offers` (in the notification scheduler loop) called `permissions_manager.is_feature_enabled()`, a sync method wrapping `with DatabaseSession()`.

**How to apply:** Any function that is `async def`, or any code that runs inside the bot's background task loops, must use `AsyncDatabaseSession` (non-blocking, `asyncio.sleep` retries) from `database.py`, never `DatabaseSession`. When auditing for this bug, grep for `with DatabaseSession()` across the whole codebase (cogs/, utils/), not just the file currently being debugged — treat one occurrence as a signal to sweep the rest. Also check plain (non-async-named) manager/helper classes with DB-backed caching methods called from async code — a sync method on a manager object is just as capable of blocking the event loop as a bare `async def` with a blocking call inside it. After fixing one blocking call, don't assume the flapping is resolved until production logs show a clean multi-hour stretch — recurring "heartbeat blocked" + "Loop thread traceback" entries pointing at a *different* file/line than the one just fixed mean there's another instance of the same bug.

Test-mock caveat: unit tests that `patch("...DatabaseSession", ...)` with a fake context manager must also patch `AsyncDatabaseSession` at the same import path, and the fake class needs both `__enter__/__exit__` and `__aenter__/__aexit__` so it works regardless of which session type the code under test uses.

**Deeper gotcha — `AsyncDatabaseSession` itself is NOT a complete fix.** Its `__aenter__`/`__aexit__` only wrap the *retry-wait* sleeps in `asyncio.sleep`; the actual `session.query()/commit()/close()` calls made by caller code inside the `async with` block, and the connection/commit/close inside `__aenter__`/`__aexit__` on a normal (non-retry) path, are still plain synchronous SQLAlchemy calls that block the event loop for the full DB round-trip. Confirmed in production via a "Loop thread traceback" pointing straight at `AsyncDatabaseSession.__aexit__` (`database.py`) called from `utils/server_permissions.py`, well after that file had already been "converted" to `AsyncDatabaseSession`. When the DB (Neon) is slow/cold, this still stalls the gateway heartbeat exactly like the old bug.

**Real fix:** use `database.run_db(func, *args)` instead — it moves the ENTIRE operation (get session, run `func(session, ...)`, commit, close, and any retry sleeps) into a background thread via `loop.run_in_executor`, so nothing touches the event loop. `func` must be a plain sync function taking `session` first and must not call commit/rollback/close itself. When migrating a call site: turn the body of the old `async with AsyncDatabaseSession() as session: ...` block into a nested `def _work(session): ...` (expunge any ORM objects you need to keep) and call `await run_db(_work)`. Treat every remaining `AsyncDatabaseSession` usage in the codebase (as of 2026-07-03, still present in `cogs/notification_commands.py` and `utils/twitch_chat_monitor.py`, dozens of call sites) as still carrying this latent risk until migrated to `run_db`.
